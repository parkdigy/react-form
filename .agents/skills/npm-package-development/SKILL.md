# npm 패키지 코딩 절차

## 사용 시점

이 저장소에서 컴포넌트 추가, 버그 수정, 공개 타입, 의존성 또는 빌드·배포 설정을 변경할 때 사용한다. 문구나 주석만 바꾸는 작업은 관련 경로와 내용만 확인한다.

## 필요한 입력

- 사용자 요청과 완료 조건
- 현재 작업 트리 상태 및 관련 구현·테스트·설정
- React, 브라우저, Node 및 패키지 소비 환경의 지원 요구사항

먼저 [저장소 지침](../../../AGENTS.md)과 [프로젝트 구조](../../../docs/agents/project.md)를 읽는다.

## 진행 방식

분석 → 구현 → 검증 → 보고 순서로 수행한다. 작은 작업은 대화 안에서 결과를 정리한다. 여러 세션에 걸치거나 중단 후 인계가 필요한 작업만 [작업 기록 양식](templates/task.md)을 저장소 루트의 `_workspace/<작업명>/task.md`로 복사해 유지한다. 작업명은 경로로 안전한 짧은 영문·숫자·하이픈 조합을 사용한다. 서로 다른 작업 기록을 덮어쓰지 않는다.

### 1. 분석

`git status --short`를 읽고 요청 범위와 기존 변경을 구분한다. 관련 소스, 예제, 테스트 유무와 설정을 추적해 기대 동작, 수정 파일, 검증 방법을 정한다. 결과는 짧은 변경 계획으로 남긴다. 해결 방향을 바꿀 중요한 정보가 없을 때만 사용자에게 질문한다.

### 2. 구현

- 공개 컴포넌트와 타입은 `src/`에 구현하고 `src/index.ts`의 내보내기를 확인한다. 타입만 내보내는 경우 `export type`을 사용한다.
- 동작 변경은 실제 공개 API를 호출하는 적절한 테스트로 확인한다. 현재 테스트 파일과 npm `test` 스크립트가 없고 Jest는 `.tsx`를 변환하지 않으므로 테스트에 필요한 실행 명령과 환경도 마련한다.
- 사용 방법이나 API가 바뀌면 README와 소스를 직접 가져오는 예제의 영향을 확인해 필요한 만큼 갱신한다.
- React와 React DOM의 peer dependency 범위, 예제의 React 버전 일치와 중복 여부를 확인한다. 예제는 `@pdg/react-admin-layout`과 그 MUI·Emotion·React Router·SimpleBar peer 의존성을 사용한다.
- 의존성 변경 시 루트와 예제의 직접 사용처, 빌드·설정에서 간접적으로 필요한 패키지, peer 범위와 Node 호환성을 확인한다. `npm outdated`의 최신 버전을 무조건 적용하지 않는다. 설치된 트리는 각 디렉터리에서 `npm ls`로 확인하고 호환되지 않아 유지한 버전과 이유를 기록한다.
- `package-lock.json`은 Git 제외 대상이다. 기존 로컬 잠금 파일이 현재 `package.json`과 다를 수 있으므로 설치·감사 시 사용한 잠금 파일과 옵션을 확인한다. 기존 잠금 파일과 `node_modules`를 무심코 삭제하지 않는다.
- `dist/`를 직접 편집하지 않는다. 설정 문제는 요청과의 관련성을 판단해 변경 범위를 정한다.

### 3. 검증과 검토

`AGENTS.md`의 루트와 예제 타입·lint 명령을 실행하고 변경에 적합한 테스트를 실행한다. 라이브러리 빌드 변경에는 Rollup 번들 확인을, 예제 변경에는 예제 Rspack 빌드를 추가한다. 배포 설정을 바꿀 때는 배포 파일 목록과 실제 소비자의 import·require·타입 해석도 확인한다.

실패하면 코드 회귀, 기존 결함, 환경 오류를 증거로 구분한다. Watchman 접근 오류에는 Rollup을 별도 실행하고 대체 검증임을 기록한다. 예제의 전체 빌드는 루트 `index.html`과 `404.html`을 덮어쓰므로 실행 전 확인한다. 개발 서버 감시 오류는 환경 오류와 구분하고, 폴링으로 우회한 경우 그 사실을 기록한다. HTTP 응답만으로 렌더링이나 HMR을 검증했다고 보고하지 않는다. 원인이 불명확하면 실패 명령·오류·남은 확인을 보존하고 통과로 표시하지 않는다. 실패를 숨기기 위해 검사 설정을 완화하지 않는다.

마지막으로 diff를 읽어 요청 범위, 공개 API 누락, 생성물 수정, 기존 변경 훼손 여부를 검토한다. 결과는 검증 명령별 성공·실패·미실행 기록과 남은 위험이다.

### 4. 완료 또는 인계

변경 목적, 주요 파일, 검증 결과, 미확인 사항을 한글로 보고한다. 중단 시 작업 기록에 완료한 내용과 다음 행동을 남긴다. 기록을 읽는 다음 에이전트는 현재 작업 트리부터 다시 확인한다.
